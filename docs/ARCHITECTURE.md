# VICE-MIND Architecture

## What This Project Is

VICE-MIND is a Phase 1 prototype for a local Tommy Vercetti decision agent. It
does not yet control Grand Theft Auto: Vice City. Instead, it uses a small
simulated world to prove this pipeline:

```text
WorldState -> perceive -> local Qwen model -> JSON decision -> act -> WorldState
```

The current model is an imitation model. Its training labels come from rules
written in `generate.py`; it is not learning from game rewards and it is not
yet reasoning from Machiavelli's *The Prince*.

## Repository Map

- `world.py`: Pydantic models for Tommy, nearby entities, and the simulated
  world.
- `generate.py`: deterministic synthetic-data generator for Phase 1.
- `dataset/phase1.jsonl`: 5,000 generated situation/decision examples.
- `train.py`: Qwen fine-tuning with LoRA and a merged local output model.
- `agent.py`: LangGraph orchestration and local inference.
- `run_sandbox.py`: one end-to-end inference cycle.
- `test_scenarios.py`: eight qualitative scenarios, not an automated accuracy
  benchmark.
- `tests/`: unit tests for perception, validation, JSON parsing, and the
  simulated car action.
- `pyproject.toml`: project metadata and dependencies for `uv`.
- `uv.lock`: exact dependency resolution generated by `uv`.

## Runtime Flow

### 1. World state

`WorldState` contains Tommy's state, nearby entities, an event log, the last
decision, and a tick counter. `Entity.attributes` is intentionally flexible so
cars, police, pedestrians, and future game objects can share one representation.

### 2. Perception

`agent.perceive()` converts the structured Pydantic model into plain text. It
lists Tommy's location and status, followed by every nearby entity and its
attributes. This text is the model's complete observation.

### 3. Decision

`agent.decide()` loads the model lazily from `TOMMY_MODEL_DIR`, applies the Qwen
chat template, and performs deterministic generation (`do_sample=False`). The
response is expected to be one JSON object with `action`, `target_id`, and
`justification`.

`_extract_json()` handles exact JSON and a simple JSON object embedded in extra
text. `_validate_decision()` replaces unknown actions with `wait`, removes
unknown target IDs, and supplies a fallback justification.

### 4. Action

`agent.act()` is currently a shallow simulator. `steal_car` changes Tommy's
vehicle and removes the selected car. Every other action mainly appends a log
message. The tick and `last_decision` are updated, then the graph ends.

### 5. Graph

`build_graph()` creates this LangGraph:

```text
START -> perceive -> decide -> act -> END
```

There is no loop back to perception, so this is one decision cycle rather than
continuous autonomy.

## Training Flow

1. `generate.py` chooses one of twelve scenario types and randomizes its
   details with a seeded `random.Random` instance.
2. Each scenario is paired with a hand-written action and short reason.
3. `train.py` loads the JSONL data and creates a 90/10 train/test split.
4. Each example is formatted with Qwen's chat template and truncated to 384
   tokens.
5. LoRA is attached to Qwen attention and MLP projection layers.
6. Hugging Face `Trainer` fine-tunes only the adapter parameters using FP16.
7. The adapter is merged into the base model and saved to
   `models/tommy-phase1`.

The learned behavior should therefore be understood as a compressed version of
the generator's policy. A model that predicts the labels well has not
necessarily learned a robust strategy for a real game.

## What It Does Well

- Clear separation between state, perception, decision, and action.
- Local inference after model files are available.
- Small Qwen checkpoint and LoRA make experimentation possible on modest GPUs.
- Structured output gives the future action layer a stable high-level contract.
- Seeded generation makes the Phase 1 dataset reproducible.

## What It Does Not Do Yet

- Read state from reVC or the original game.
- Send keyboard, controller, navigation, driving, combat, or animation commands.
- Run continuously or react to consequences over multiple steps.
- Simulate damage, deaths, police escalation, movement, cash, or world changes
  for most actions.
- Validate whether a target is the correct type for the selected action.
- Measure decision accuracy, target accuracy, latency, safety, or robustness.

## Recommended Next Technical Boundary

Before game integration, make the simulator a real environment:

```text
observation -> action -> transition -> reward/metrics -> next observation
```

Add action-specific validation, deterministic transitions, a multi-step runner,
and machine-readable evaluation. Only then should the game-state adapter and
game action adapter be introduced.
